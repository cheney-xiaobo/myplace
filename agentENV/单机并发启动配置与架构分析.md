# AgentENV 单机并发启动配置与架构分析

> 范围：单机 100–500 并发启动、启动链路、warmup 起始配置、同一/多个镜像、x86_64/ARM64 差异、主机容量和压测方法。
>
> 基线为此前成功获取的 `origin/main`：`34cdc8098096726646853a18cec7ae143995dcef`。后续刷新远端时网络超时，因此不覆盖该提交之后的改动。本文的池水位和调参值是**未实测的压测起点**，不是生产最优值。
>
> 相关笔记：[[并发效率观测与 envd 等待分析]]、[[并发启动控制点分析]]、[[沙箱拉起全流程]]、[[Ublk 设备管理]]。

以下把“一个/多个镜像”理解为：**N 个 sandbox 使用同一镜像/模板，还是分散到多个镜像/模板**。

## 一、核心结论

1. **100–500 并发启动，优先测预构建模板的 `/sandboxes`，不要和 `/sandboxes/cold` 混为一谈。** 前者是快照恢复；后者还包括 registry manifest 请求、可能的 OCI→OverlayBD 转换、完整 guest boot，而且不会使用 Firecracker 进程池。
2. **默认 `pool.low=2/high=64` 不适合直接承接 100–500 的首轮突发。** 但 warmup 只预热网络槽、ublk 设备和未配置的 Firecracker 进程，**不是预热了某个镜像的完整 sandbox**。
3. **同一模板通常比多模板更有利，主要优势是内存快照设备和 page cache 共享。** 全部缓存和资源都热起来以后，差距会缩小，最终仍受每实例的 rootfs 设备、COW upper、网络、快照恢复和 envd 初始化限制。
4. **500 并发首先是主机容量和排队问题，其次才是某个超时参数。** 默认每实例 2 vCPU、1 GiB，500 个就是 1000 个 guest vCPU、500 GiB 的逻辑 guest 内存。快照共享和 COW 会降低实际内存占用，但不能据此假设任意超卖都安全。
5. **不能笼统说 x86 一定比 ARM 快，或 ARM 一定更省。** ISA、物理核/SMT、NUMA、host page size、KVM/PVM、存储和镜像内容都会干扰结果，必须按同档位硬件分别实测。

## 二、启动链路里真正影响并发的工序

### 1. 模板启动 `/sandboxes`

主路径为：

```text
load_snapshot
  → 恢复/准备 volume（如果有）
  → 创建 rootfs OverlayBD/ublk runtime
  → 获取 Firecracker 暖进程
     未命中：创建网络命名空间、启动 FC、等待 API socket
  → 获取或创建共享内存快照 ublk 设备
  → load_snapshot + resume
  → envd 健康检查和初始化
  → Running
```

代码入口见 `src/api/impls/sandbox.rs:1008-1124`，核心恢复路径见 `src/sandbox/firecracker/sandbox.rs:1962-2336`。

关键影响点：

- **快照解析**：POSIX 后端主要生成本地 runtime 配置；同一 cache key 的并发 materialization 会合并，见 `src/snapshot/artifact_cache.rs:130-225`。OSS 冷缓存则还要下载对象并填充本地缓存。
- **rootfs 仍是每 sandbox 一个独立可写设备和 upper**，不是同模板只创建一个 rootfs 设备。
- **内存设备可以按模板共享**。内存快照通过 file-backed mmap 恢复，写入时 COW 为匿名页，同模板共享内存 ublk 和 page cache，见 `docs/src/internals/architecture.md:112-118`。
- **FC 池命中只省去进程创建和 API socket 等待**，并不会跳过 rootfs、内存设备、快照 load/resume 和 envd。
- API 要等 envd 健康检查及初始化完成后才返回 Running，见 `src/orchestrator/service.rs:2495-2569` 和 `src/sandbox/firecracker/sandbox.rs:908-959`。

### 2. 网络冷路径是明显瓶颈

网络池未命中时，`allocate_any()` 会同步执行 `create_network()`；后者创建线程并 `join()`，包括 netns、veth、netlink 和 iptables 初始化：

- `src/sandbox/network/manager.rs:232-299`
- `src/sandbox/network/slot.rs:118-186`

这意味着高并发 cache miss 不只是内核网络操作慢，**还会阻塞正在执行启动请求的 Tokio worker**。

另外：

- 网络池后台补充是串行循环。
- 默认无自定义 egress 规则时，暖槽上的 `set_egress_policy()` 可以直接返回。
- 如果配置了 `allowOut/denyOut`、域名规则或 egress proxy，每次启动还会增加线程、iptables 和 DNS/proxy 工作，见 `src/sandbox/network/slot.rs:459-518`。

因此应把“默认网络策略”和“自定义域名 egress 策略”分成两个基准。

### 3. 冷镜像启动还有 registry 惊群

`/sandboxes/cold` 会先执行 `resolve_rootfs`，见 `src/api/impls/sandbox.rs:666-800`。

即使转换结果已经缓存，代码仍然**先抓 registry manifest，再查本地缓存**，见 `src/image/resolver.rs:191-244` 和 `src/image/resolver.rs:320-378`。

所以 500 个相同冷镜像请求仍可能产生 500 次 manifest 获取和 `regctl` 进程创建。固定 digest 能稳定缓存身份，**但不会消除这次 registry 请求**。

OCI 转换有按镜像锁，转换期间其他同镜像请求等待并最终复用结果，见 `src/image/cache/service.rs:160-174` 和 `src/image/cache/service.rs:1096-1113`。

## 三、warmup 池应该配多少

### 先理解当前算法

`low_watermark` 是初始补充目标；获取压力会让目标按倍数向 `high_watermark` 增长，而且增长后在进程生命周期内不自动降回，见 `crates/warm-pool/src/lib.rs:82-123` 和 `crates/warm-pool/src/lib.rs:166-224`。

因此：

- 默认值不是“始终只有 2 个”，而是**从 2 开始，压力下最多增长到 64**。
- 但首轮 100–500 突发很可能远快于后台补池，仍会大量 miss。
- 服务启动时 `prime()` 只等待到 `low_watermark`，且最多等 10 秒；超时后继续以部分预热状态运行，见 `src/sandbox/firecracker/pool.rs:184-233` 和 `src/bin/server.rs:96-105`。
- block 池需要第一次知道可复用镜像/尺寸后才开始补充，并且补充循环是串行的，见 `storage/ublk-daemon/src/server.rs:1854-1928`。

### 推荐起始值

以下是**压测起点，不是实测最优值**。`high` 大致给突发量 20%–28% 余量。

| 单批突发 N | 重复突发压测 `low/high` | 要求首轮尽量全命中 `low=high` | `fill_concurrency` 起点 |
| ---: | ---: | ---: | ---: |
| 100 | `32 / 128` | `128` | 8 |
| 200 | `64 / 256` | `256` | 8 |
| 300 | `64 / 384` | `384` | 16 |
| 500 | `128 / 640` | `640` | 16，再 A/B 32 |

500 并发的重复压测配置示例：

```toml
[pool]
low_watermark = 128
high_watermark = 640

[pool.network]
maintenance_enabled = true

[pool.block]
enabled = true
# startup_prewarm 建议先保持能力检测默认值

[pool.firecracker]
enabled = true
startup_prewarm = true
fill_concurrency = 16
```

使用时要区分：

- **重复突发**：先跑一轮不计数的 priming，再等待实际池水位稳定，之后测正式轮次。
- **服务启动后的第一轮就必须命中**：使用 `low=high`，先启动一个 canary sandbox，触发共享内存设备和 block 池的镜像形状初始化，然后等待预热完成再发整批请求。
- **纯 `/sandboxes/cold` 测试**：Firecracker 进程池不参与 fresh boot，建议禁用它或保持很小，避免大量暖 FC 进程及其占用的网络槽做无用功。网络和 block 池仍有价值。

`fill_concurrency` 只控制 FC 补池批次，见 `src/sandbox/firecracker/pool.rs:255-295`。它不会让串行的 network/block 补充也同比加速，所以不要期待从 4 调到 32 后整个预热快 8 倍。

### 其他注意事项

- 这些水位是**节点级共享值，不是每镜像一份**，不要按镜像数量直接相乘。
- 如果内核不支持 `UBLK_F_UPDATE_SIZE`，block 池只选取虚拟尺寸匹配的设备；多种磁盘尺寸会降低有效命中率，见 `storage/ublk-daemon/src/server.rs:1824-1833`。此时最好统一测试磁盘尺寸。
- 640 个暖条目会带来大量 FC 进程、netns、FD、ublk 队列和 runtime 线程。ublk 默认每设备 1 个队列、depth 16、最大 I/O buffer 256 KiB，见 `storage/ublk/src/ctrl.rs:108-130`。高水位不是零成本。
- 暖 FC 尚未配置 guest 内存，不等于立即占用 `640 × 1 GiB`；但恢复之后内存会按实际触及和写入页增长。

## 四、一个镜像快，还是多个镜像快

### 模板快照启动：同一模板通常更快

优势主要来自：

- 同模板共享内存快照 ublk 设备。
- 同一份内存快照页和 rootfs lower 更容易复用 page cache。
- 多模板会增加独立内存设备、热内存集、layer 工作集和缓存压力。

但有一个首轮细节：**共享设备建立前存在并发重复创建窗口**。节点和 daemon 都专门处理了“另一个并发调用已经创建成功”的情况，冗余设备随后会被清理：

- `src/sandbox/ublk/device.rs:696-730`
- `storage/ublk-daemon/src/server.rs:1576-1637`

所以不能假设首轮 500 个同模板请求一定只创建一个内存设备。**先运行一个 canary 并保持到整批启动结束，再发剩余请求**，能减少这个重复创建窗口。

### 冷镜像启动：同一镜像通常仍有优势，但不是绝对

同一镜像可以复用转换结果和 layer cache；不同镜像的转换可以并行，因此多镜像在 CPU、网络和 registry 容量充足时，总 wall time 不一定更差。

但多镜像通常会增加：

- manifest 和 layer 请求量；
- OCI 转换 CPU/磁盘工作；
- 唯一 layer 和 remote block cache 工作集；
- registry 限流及缓存淘汰风险。

当所有镜像都已经转换、页面已缓存后，镜像数量的影响会下降；共享 base layer 的多镜像，也比完全无共享层的多镜像更接近单镜像。

**实践建议：**

- 追求启动延迟：使用预构建模板，而不是让每个请求经过冷镜像解析。
- 必须冷启动：优先 OverlayBD-native 或提前转换的镜像、就近 registry、完整且固定的镜像引用。
- 对比测试使用 `1×500`、`10×50`、`50×10`，保持镜像大小、层数、sandbox 资源一致，并分别测试“共享 base layer”和“无共享层”。

## 五、x86_64 与 ARM64 的主要差异

| 项目 | 代码事实与测试影响 |
| --- | --- |
| 原生架构 | 主线只接受 `x86_64` 和 `aarch64`，分别下载对应 FC、kernel、OverlayBD，并选择 OCI `amd64/arm64`，见 `src/setup/deps.rs:75-107`。镜像、模板和快照应按架构分别构建与预热。 |
| KVM/PVM | 两者都可使用标准 KVM；PVM 仅支持 x86_64，见 `src/setup/kvm.rs:44-80`。 |
| PVM 对比干扰 | KVM 默认 FC 为 `1.15.1-patch-v1`、guest kernel 为 6.1；PVM 使用不同 FC 和 6.12 kernel，见 `config/deps_manifest.toml:1-15`。PVM 还自动关闭 dirty-page tracking。因此 KVM/PVM 的差异不能直接归因于 CPU。 |
| 内存布局 | fresh boot 的 DAMON monitor region 在 x86 与 ARM 上不同，见 `src/sandbox/firecracker/sandbox.rs:2721-2788`。这不是“某架构天然更快”的证据，且快照恢复不走 fresh boot 参数。 |
| SMT/物理核 | guest 的 `smt` 被设置为 false，但这不等于宿主机 SMT 被关闭。x86 测试要分别记录物理核和逻辑核；不能把 2 个 SMT sibling 当成 2 个等价物理核。 |
| ARM 大小核 | 如果机器存在异构核心，500 个 VM 的调度差异可能放大 p99。应在同构核心集合上测试，或把核心类型作为单独变量。 |
| NUMA | 多路 x86 和多路 ARM 都可能遇到跨节点内存/page cache 访问。问题属于机器拓扑，不应简单归因于 ISA。 |
| Host page size | ARM64 环境可能出现 16/64 KiB host page；启动包和 dirty-page 逻辑使用 4 KiB guest 粒度，见 `storage/overlaybd/src/startup_pack.rs:9-12`。不同 host page size 会改变 fault 和缓存行为，应记录并单独验证。 |

跨架构对比时应固定：

- 物理核数、NUMA 节点数、内存和 NVMe 档位；
- sandbox vCPU/内存；
- 等价应用镜像的层数和实际大小，而不只是相同 tag；
- KVM 模式、FC/kernel/tools 版本；
- 快照后端、缓存状态和 warmup 水位；
- SMT、CPU 频率/功耗策略及 host page size。

## 六、其他需要一起调整的参数

| 参数 | 默认值 | 并发启动建议 |
| --- | --- | --- |
| 请求 `timeout` / `autoPause` | `/sandboxes` 未传 timeout 时使用 15 秒；默认到期 Pause | **每个请求显式设置足够长的 timeout，例如 900 秒**。纯启动测试可用 `autoPause=false`，避免测试中途做自动暂停和快照。默认值见 `config/default.toml:202-212`。 |
| `envd.poll_ms` | 3 ms | 500 个失败健康检查会形成探测风暴。建议 A/B `3/10/20ms`；10 ms 是合理起点，会增加少量就绪检测延迟。 |
| `envd.init_timeout_secs` | 60 s | 先保持。它主要决定失败容忍度，不会直接加快启动。 |
| `firecracker.socket_timeout_secs` | 3 s | 池命中时不走该等待。若冷路径在 CPU 饱和下确实出现 socket timeout，可 A/B 5–10 秒，但不要用延长超时掩盖排队。 |
| `firecracker.socket_poll_ms` | 1 ms | 主要影响冷启动及补池；池全命中后影响很小。 |
| `orchestrator.metrics_interval_secs` | 15 s | 纯启动基准可将 guest metrics 设为 0 做对照。500 个运行时，周期采集并发度会达到 `ceil(500/5)=100`，见 `src/orchestrator/sandbox_metrics.rs:20-25`。 |
| `snapshot.memory_startup_pack` | 按配置 | 有远程内存首次读取收益时先录制并启用；500 个同时预取也可能制造 I/O 突发，应做开关 A/B。 |
| `ublk.overlaybd.remote_io_workers` | 4 | 只对远程镜像 I/O 重点测试，可比较 4/8；本地 POSIX 热缓存不是主要调节项。 |
| `memory_snapshot.background_download.*` | enabled，16 MiB × 4，backend 最多 16 chunk | 下载在 envd ready 后才启动，但先完成的实例会与后启动实例竞争网络/磁盘。可测试 delay/jitter；不要盲目关闭生产下载。默认 scratch 上限为每 backend `16×16 MiB=256 MiB`，见 `docs/src/configuration/reference.md:602-639`。 |
| `ublk.overlaybd.download_enable` | false | 保持关闭做基线；开启 rootfs 后台下载会增加后台流量。 |
| `custom_extension` | 默认关闭 | 启用后 start hook 位于关键路径，必须单独记录 hook 延迟和失败率。 |
| volumes / attachedDrives | 按请求 | 每个附加盘都会增加设备准备及可能的 guest mount，不应混入基础启动对照组。 |
| `firecracker.log_level` | 默认关闭 | 基准保持关闭；Debug/Trace 会给每实例增加日志 I/O。 |
| `AENV_LOG_SPAN_EVENTS` | `off` | 保持 `off`；节点和 HTTP 指标仍应保留用于分析。 |
| `p2p.enabled` | false | 单机测试保持关闭，P2P 对单节点没有实际加速意义。 |
| `template_build.max_concurrent_builds` | 4 | 只限制模板构建，不限制 sandbox 启动。 |
| `GATEWAY_REQUEST_TIMEOUT` | 30 s | 经过 gateway 压测时应大于预期整批请求尾延迟，同时客户端超时也要放宽，否则测到的是客户端断连。 |

另外，节点启动主路径未看到全局启动并发闸。scheduler 的 `max_sandbox_starting_count` 是基于心跳快照的候选节点过滤，不是节点内的启动信号量，见 `services/scheduler/internal/filter.go:28-46`。**单机直连测试需要由客户端或额外 admission controller 控制并发。**

## 七、主机容量和压测方法

### 1. 先检查内核和运行环境

`setup-host` 包含以下容量阈值：

- ARP neigh：`4096 / 8192 / 16384`
- `nf_conntrack_max = 1048576`
- `kernel.pid_max = 4194304`
- `fs.inotify.max_user_instances = 8192`

见 `src/setup/network_capacity.rs:18-63`。

容器内默认跳过自动 sysctl 调整，因此 Docker 压测时要确认这些值是在**宿主机**上生效，而不是只看容器里的 AgentENV 配置。

内存规划应看：

```text
共享模板热页
+ 每个 sandbox 的私有 dirty/working-set 页
+ FC/ublk 进程、页表、队列和网络开销
+ rootfs/快照 page cache
+ 宿主机安全余量
```

而不是只看 `N × 1 GiB`，也不能把快照共享理解为内存零成本。

### 2. 推荐测试矩阵

并发级别：

```text
1、10、50、100、200、300、500
```

每个级别至少区分：

1. `/sandboxes` 与 `/sandboxes/cold`。
2. 冷缓存首轮与热缓存重复轮。
3. 默认池、预热后池、不同 `fill_concurrency`。
4. 单镜像与多镜像。
5. 不同 sandbox vCPU/内存档位。
6. guest metrics 开关、envd poll 间隔。
7. POSIX 与 OSS。
8. 默认网络策略与自定义 egress。

同时区分两种负载：

- **Burst-and-hold**：同时创建 N 个，全部保持 Running，直到最后一个 ready 后再稳定运行一段时间。测真实单机容量。
- **Closed-loop create/delete**：不断创建、ready、删除。测持续吞吐及池复用，但不能代替 N 个同时存活的容量测试。

现有 `crates/benchmarks/benches/snapshot_benchmark.rs:363-432` 固定为 50 并发，而且把各 worker 的样本求和平均；另一路径按样本序号聚合平均值，见 `crates/benchmarks/benches/snapshot_benchmark.rs:530-605`。它还是 backend 级测试，不包含完整 HTTP/API 路径，因此不足以回答 100–500 的 p99 和整批 wall time。

### 3. 必看指标

- 每请求延迟：p50/p90/p95/p99/max。
- 整批 wall time、ready/s、成功率和错误类型。
- `agentenv_sandbox_stage_duration_seconds`：
  - `create_warm/load_snapshot`
  - `create_warm/create_sandbox`
  - `create_cold/resolve_rootfs`
  - `create_cold/create_sandbox`
