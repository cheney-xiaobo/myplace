# AgentENV 并发启动流程与并发控制点分析

> 分析对象：普通 `/sandboxes` 快照恢复、`/sandboxes/cold` 冷启动，以及与启动并发相关的调度、warm pool、镜像、快照、ublk/OverlayBD、envd 和后台指标路径。
>
> 源码基线：此前成功获取的 `origin/main`，提交 `34cdc8098096726646853a18cec7ae143995dcef`。后续远端刷新曾超时，因此不保证覆盖该提交之后的新改动。文中的改进建议不代表已实施或已验证。
>
> 相关笔记：[[单机并发启动配置与架构分析]]、[[并发效率观测与 envd 等待分析]]、[[Ublk 设备管理]]。

## 核心结论

**当前普通 `/sandboxes` 和 `/sandboxes/cold` 没有统一的“最多允许 K 个 sandbox 同时启动”信号量。**

现有机制主要是：

1. 按镜像或缓存键去重；
2. warm pool 补池限速；
3. 存储和 DNS 的局部 I/O 限流；
4. 单 sandbox、单镜像的互斥保护。

因此，500 个请求仍然可能同时进入设备创建、快照恢复和 envd 健康等待。

需要特别区分以下概念：

| 机制 | 解决的问题 | 是否限制普通启动总并发 |
| --- | --- | --- |
| 全局或节点级 admission semaphore | 限制同时启动的 sandbox 数 | 当前普通启动路径没有 |
| Warm pool watermark | 维持 idle 资源数量 | 否 |
| Warm pool `fill_concurrency` | 限制后台补池速度 | 否 |
| `try_acquire()` | 非阻塞取用已有 warm 资源 | 否；miss 后直接 cold fallback |
| per-key singleflight | 合并相同 artifact 的 materialization | 否 |
| per-image mutex/RwLock | 保护镜像转换或存储栈状态 | 否 |
| I/O semaphore/worker | 限制局部下载、远程 I/O 或 DNS 并发 | 只限制对应局部资源 |
| per-sandbox mutex | 串行化同一个 sandbox 的生命周期操作 | 否 |

## 一、启动准入：基本没有全局限流

### 1. Orchestrator 每个创建请求独立启动任务

`create_sandbox()` 为每个请求 `tokio::spawn` 一个 cancellation-safe task，没有全局启动 semaphore，也没有有界等待队列：

- `src/orchestrator/service.rs:288-314`
- `src/orchestrator/service.rs:424-434`

这意味着：

- 客户端同时发多少，服务端就可以接收多少启动任务；
- 客户端断开或停止等待后，后台启动任务仍会继续；
- 不能用“客户端已经超时”推断服务端启动压力已经消失。

`launch_sandbox()` 内也没有跨 sandbox 的全局锁，`start_nowait()` 可以并行执行，见 `src/orchestrator/service.rs:2399-2435`。

### 2. 单 sandbox 锁不是全局启动锁

每个运行中的 sandbox 有独立的：

```rust
Arc<Mutex<Box<dyn SandboxBackend>>>
```

它用于串行化**同一个 sandbox** 的 wait、pause、metrics 等操作，不会串行化不同 sandbox。

而且这个 handle 是在 `start_nowait()` 完成后才插入 map，所以并不限制最重的启动准备阶段，见 `src/orchestrator/service.rs:2467-2499`。

### 3. Scheduler 的限制不是严格准入信号量

集群模式有 `max_sandbox_starting_count`，但它只是根据最近一次 heartbeat 中的 `sandboxStartingCount` 筛选节点：

- 没有 heartbeat 的节点仍会被保留；
- 判断使用 `>`，等于阈值时仍可选中；
- 没有启动前的原子 reservation；
- 直连 node API 时不经过这个过滤。

见 `services/scheduler/internal/filter.go:5-35`。

所以它适合调度避雷，**不能保证节点实际启动数不超过 K**。

### 4. Template build 的限制不适用于普通启动

`template_build.max_concurrent_builds=4` 是构建会话的硬限制，达到后返回 429，见 `src/api/impls/image_build.rs:42-60`。

它不会限制 `/sandboxes` 的并发恢复。

## 二、快照和镜像：按 key 去重，不是整体串行

### 1. 快照 artifact materialization 是 per-key singleflight

同一个 cache key 同时需要生成本地文件时：

- 一个请求执行 materialization；
- 其他请求等待相同结果；
- 成功后共同复用缓存。

见 `src/snapshot/artifact_cache.rs:130-225`。

但它只合并：

- vm_state 下载；
- memory/rootfs `image.json` materialization；
- 其他缓存 artifact。

**不会合并整个 `load_snapshot()`，也不会合并后续 VM start。**

OSS 校验 managed layers 时，每次校验最多 16 个并发 `exists`，见 `src/snapshot/repository/backends/oss/resolver.rs:27-62`。不同模板之间仍可并行。

### 2. 冷镜像转换有 per-image 锁

同一个 manifest digest 的转换通过 per-image async mutex 串行化。等待者拿到锁后会重新看到已发布的缓存配置，从而复用转换结果：

- `src/image/cache/source_config.rs:19-42`
- `src/image/cache/service.rs:160-174`
- `src/image/resolver.rs:320-378`

但要注意：

- registry manifest 获取发生在转换锁之前；
- 500 个相同冷镜像请求仍可能同时启动 500 个 `regctl`；
- `GOMAXPROCS=4` 只限制每个 `regctl` 进程的 Go runtime，不限制进程数量。

见 `src/image/oci_image.rs:936-968`。

## 三、三类 warm pool：限制补池，不限制启动请求

通用 `WarmPool` 的获取操作是：

```rust
try_acquire() -> Option<T>
```

它是一个短时间的 `Mutex<VecDeque>` pop：

- 有资源立即返回；
- 没资源立即返回 `None`；
- **不会排队等待新资源**。

见 `crates/warm-pool/src/lib.rs:209-225`。

所以：

> `low_watermark/high_watermark` 控制 idle 资源目标，不是 active sandbox 并发上限。

### 各池的差异

| 池 | 后台补池控制 | 池未命中时 |
| --- | --- | --- |
| Firecracker | `fill_concurrency=4`，每批最多 4 个，批间串行 | 请求自行创建网络、FC 进程，无统一并发上限 |
| Network | 单 maintenance worker，逐个串行创建 | 请求同步创建 netns/veth/iptables，可多个 miss 并行 |
| Block/ublk | `refill_inflight` 合并补池任务，任务内逐个串行创建 | 每个请求自行创建新设备，可并行 |

对应代码：

- FC 补池：`src/sandbox/firecracker/pool.rs:255-294`
- 网络补池：`src/sandbox/network/manager.rs:307-338`
- block 补池：`storage/ublk-daemon/src/server.rs:1854-1928`

**首轮 500 突发时，限制补池并不能阻止前台 500 个 cold-miss fallback 同时发生。** 增大 `fill_concurrency` 也只会加快预热，同时可能增大瞬时主机压力。

网络另有硬容量：32768 个 slot index，slot 0 保留；耗尽后返回 `No available slots`，见 `src/cfg/network.rs:5-11` 和 `src/sandbox/network/manager.rs:271-299`。这是容量边界，不是推荐的限流手段。

## 四、ublk/OverlayBD：I/O 有局部上限，设备创建没有统一上限

### 1. ublk daemon 请求处理本身没有全局并发上限

每个 Unix socket 连接都会 `tokio::spawn` 一个 handler，见 `storage/ublk-daemon/src/server.rs:410-445`。

所以大量 runtime rootfs/memory acquire 可以同时进入 daemon。

### 2. per-image RwLock 不会串行化普通启动

acquire 时拿的是镜像锁的 **read**：

```rust
let _image_guard = image_lock.read().await;
```

只有 restack snapshot 拿 write。因此：

- 同镜像普通 acquire 可以并行；
- restack 与同镜像 open 互斥；
- 不同镜像普通 acquire 不被该锁串行化。

见 `storage/ublk-daemon/src/server.rs:1446-1497`。

另外，OverlayBD resize 有 daemon-wide mutex，因为共享一个 resize cacheDir；但快照恢复不 resize，主要影响冷启动尺寸变化。

### 3. 共享内存设备不是“创建前 singleflight”

同模板共享内存设备的逻辑是：

```text
检查 active_shared
→ 未找到则创建/取用设备
→ 插入 active_shared
→ 如果此时发现别人已插入，停止自己的冗余设备
```

见 `storage/ublk-daemon/src/server.rs:1576-1648`。

AgentENV 侧的 weak-map 也有类似的“创建后选胜者”逻辑，见 `src/sandbox/ublk/device.rs:703-730`。

所以它是**创建后仲裁去重**，不是创建前合并。同模板第一轮同时 acquire 仍可能出现重复设备创建和销毁窗口。

### 4. OverlayBD 下载有真正的 semaphore

每个 `FileCacheBackend` 的后台下载调度器有：

- `maxConcurrentFiles=8`：并发 layer task；
- `maxInflightBlocks=16`：所有任务共享的 chunk 上限；
- startup-pack task 默认最多占 file budget 的四分之一，即默认 2 个；
- 不同 global config/cache backend 可以有各自独立的预算。

见 `storage/overlaybd/src/backend/cache/bk_download.rs:125-205`。

其他控制：

- `remote_io_workers=4`：每个 ImageService 的远程 I/O runtime worker 数，限制执行线程，不是请求队列上限，见 `storage/overlaybd/src/image/image_service.rs:119-149`。
- 本地 startup-pack 预取有进程级 4-read semaphore，见 `src/sandbox/firecracker/startup_pack.rs:279` 和 `src/sandbox/firecracker/startup_pack.rs:381-384`。
- 每个 ublk queue 还有 queue depth/slot 限制，但这是单设备 I/O 在飞控制，不是 sandbox 启动限流。

## 五、envd 和辅助路径

### 1. envd 健康等待没有并发 semaphore

每个正在启动的 sandbox 都独立执行健康检查循环：

- 单次最多 1 秒；
- 默认失败间隔 3 ms；
- 没有全局健康探测并发上限；
- 没有指数退避或 jitter。

见 `src/sandbox/envd.rs:118-160`。

`envd.poll_ms` 只控制重试间隔，**不控制有多少 sandbox 同时等待 envd**。

`envd.init_timeout_secs` 只决定健康等待最多持续多久；延长它不会加快启动，也不是启动并发控制参数。

### 2. 域名 egress 的 DNS 有固定上限

只有使用域名 egress/proxy 时才相关：

- queue capacity：128；
- 最大 DNS in-flight：16；
- 队列 `try_send` 满时会直接失败，而不是无限排队。

见 `src/sandbox/network/resolver.rs:17-21` 和 `src/sandbox/network/resolver.rs:188-224`。

默认数字 IP 的 envd 健康检查不经过这个 resolver。

### 3. 后台 guest metrics 也会影响压测

周期 metrics 采集并发为：

```text
ceil(running_sandbox_count / 5)
```

500 个 Running 时最多 100 个并发采样，每次请求超时 200 ms；通过 `try_lock` 避免等待正在执行生命周期操作的 sandbox：

- `src/orchestrator/sandbox_metrics.rs:20-25`
- `src/orchestrator/sandbox_metrics.rs:162-188`

它不控制启动，但会给 envd 和网络增加背景负载。做纯净启动基准时，可以把 `metrics_interval_secs=0` 作为一次 A/B 对照，而不是生产上一律关闭。

## 六、最值得关注的“控制缺口”

对 100–500 并发，当前最关键的是这几个：

1. **没有 node-level launch admission**：客户端并发可以完整传递到服务端。
2. **warm pool miss 直接 cold fallback**：不会因池空而等待或拒绝。
3. **网络和设备的前台创建没有统一并发上限**。
4. **共享内存设备是创建后去重，不是创建前 singleflight**。
5. **envd 等待和健康探测没有全局并发控制**。
6. **fork 也使用 `join_all` 启动全部 child**，单次最多 100 个 child，内部没有额外启动 semaphore，见 `src/sandbox/firecracker/sandbox.rs:506-520`。

## 七、如果后续要增加并发控制

最有效的是两级控制：

### 1. 整批启动准入

在 API 最前面获取 permit，覆盖镜像/快照解析一直到 Running，防止 `load_snapshot` 和 registry 阶段无界扩张。

它需要明确：

- 节点级最大在飞启动数；
- 有界等待队列；
- 排队超时和拒绝策略；
- 客户端断开后的任务处理策略；
- 按快照恢复与冷启动分别统计的在飞数。

### 2. 重型 `start_nowait` 独立限流

限制 netns、ublk、FC load/resume 的并发，permit 在 resume 后释放；envd 等待可以允许更大的并发，避免 I/O 等待长期占用重型启动名额。

同时需要补充：

- 启动 admission 在飞数；
- 排队长度和排队时长；
- 各阶段在飞数；
- 因队列满或排队超时产生的 429/失败数；
- warm pool 命中率和 cold-miss fallback 数；
- envd 健康等待时长、尝试次数、超时数和错误类别。

**只调 `high_watermark` 或 `fill_concurrency`，不能形成真正的 500 并发保护闭环。**

## 八、调参和压测时的判断边界

| 参数或机制 | 能改变什么 | 不能据此推断什么 |
| --- | --- | --- |
| `pool.low_watermark/high_watermark` | idle warm 资源目标和补池触发 | 不能限制 active sandbox 数 |
| `pool.firecracker.fill_concurrency` | FC 后台每批补池并发 | 不能限制前台 cold-miss 启动 |
| `envd.poll_ms` | 单次健康检查失败后的重试间隔 | 不能限制同时健康等待的 sandbox 数 |
| `envd.init_timeout_secs` | 健康等待的超时预算 | 不会提升启动速度 |
| `max_sandbox_starting_count` | scheduler 根据 heartbeat 筛选节点 | 不是节点原子 admission 上限 |
| `template_build.max_concurrent_builds` | 模板构建并发 | 不适用于普通 sandbox 启动 |
| `remote_io_workers` | 每个 ImageService 的远程 I/O worker 数 | 不是 sandbox 请求队列上限 |
| DNS queue/in-flight | 域名解析排队与在飞请求 | 默认数字 IP envd 检查不经过它 |
| `metrics_interval_secs` | 后台指标采样频率 | 不是启动限流参数 |

在缺乏统一 admission 的当前版本，外部压测客户端或网关的并发上限是最直接的保护措施，但它不能替代服务端背压：客户端超时或断开后，已经接收的启动任务仍可能继续运行。

建议实测时分别记录：

- 客户端发出并发与服务端实际在飞启动数；
- snapshot artifact 命中率、warm pool 命中率和 cold fallback 数；
- 镜像解析、设备准备、FC load/resume、envd 健康、`/init`、挂载到 Running 的分阶段时延；
- daemon 请求在飞数、OverlayBD 远程读取和后台下载队列；
- CPU run queue、iowait、内存压力、块设备 await/aqu-sz、网络重传及宿主机错误日志。

这些数据才能判断当前瓶颈是缺少准入、预热不足、存储 I/O 饱和，还是 envd/guest 侧等待。具体指标与 PromQL 见 [[并发效率观测与 envd 等待分析]]。
